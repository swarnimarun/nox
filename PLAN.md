# Nox implementation plan

## Product thesis

Nox should make NixOS understandable and operational for people who want one
reproducible Linux platform across a server, workstation, WSL distribution,
or isolated workspace. The product is the contracts and lifecycle around
NixOS; it is not a new package manager, hypervisor, filesystem, or container
runtime.

## Architecture decision

The original “five modes” are being normalized into three independent axes:

| Axis | Initial values | Meaning |
| --- | --- | --- |
| Profile | server, desktop, gaming, workspace, recovery | What the machine is for |
| Capability | storage, shares, apps, virtualization, development, remote-management | Which composable features are enabled |
| Target | metal, iso, qcow2, wsl, oci | Where the system runs or which artifact is built |

“Bootable” is a target/profile combination, not a separate operating system.
“Isolated” is a workspace capability/backend, not a second configuration model.

## Ownership boundaries

Nix configuration is desired state. Runtime APIs, health, process state, and
operation progress are observed state. `noxctl` can safely update the stable
TOML schema, while advanced `.nix` files remain user-owned. A future daemon
must never rewrite arbitrary Nix source.

Nox delegates implementation-heavy primitives to established projects:

| Concern | Delegated to |
| --- | --- |
| OS composition and packages | NixOS / nixpkgs |
| Disk declarations and installation | Disko and nixos-anywhere |
| Hardware facts | nixos-facter |
| VMs and system containers | Incus, QEMU/KVM |
| Application containers | Podman |
| Storage | ZFS and Btrfs |
| Secrets and boot security | sops-nix and Lanzaboote |
| Development environments | Nix, devenv, Home Manager |
| Backups and VPN | Restic, ZFS snapshots, WireGuard/Tailscale |

## Upstream lessons

- NixOS 26.05 is the current stable release for this project’s initial
  channel, and NixOS already provides composable modules and integration-test
  infrastructure. See the [26.05 release announcement](https://nixos.org/blog/announcements/2026/nixos-2605/).
- Flakes provide a uniform project shape and lock files, but remain an
  explicit Nix interface rather than the only user-facing configuration. See
  the [official Flakes documentation](https://wiki.nixos.org/wiki/Flakes).
- Disko and nixos-anywhere should own disk declarations and remote install
  mechanics; Nox should add UX and safety checks around them ([disko](https://github.com/nix-community/disko),
  [nixos-anywhere](https://github.com/nix-community/nixos-anywhere)).
- deploy-rs and Clan demonstrate why remote deployment needs confirmation,
  health checks, and a recovery path ([deploy-rs](https://github.com/serokell/deploy-rs),
  [Clan deployment](https://clan.lol/docs/26.05)).
- The CLI must be `noxctl`, not `nox`: the name `nox` is already used by a
  mature Python development-session tool.

## Implementation status

The scaffold milestone below is historical. The current component-by-component
plan and acceptance gates are in [the implementation plan](docs/operations/implementation-plan.md).
Build/image/lock/install/generations now have implementations; apply/rollback
remain reserved. Artifact support requires runtime evidence, not just modules.

## Initial milestone: prove the core thesis

The first milestone is deliberately small:

- versioned TOML configuration with validation;
- pure profile/capability/target planning;
- `noxctl init`, `validate`, `plan`, and `doctor`;
- NixOS core module plus server, desktop, recovery, metal, ISO, and qcow2
  modules;
- reproducible developer shell and CI checks;
- architecture/state-ownership RFCs and a smoke-test path.

The reserved lifecycle commands are intentionally not implemented yet:
`build`, `image build`, `apply`, `generations`, and `rollback`.

## Next milestones

### Phase 1 — contracts and build

1. Add a committed `Cargo.lock` generated by Cargo.
2. Decide the supported nixpkgs release and commit `flake.lock`.
3. Add a real Nix-to-TOML configuration bridge.
4. Implement `noxctl build` as a pure evaluation/build operation.
5. Add NixOS VM tests for each profile.

### Phase 2 — installation and safe activation

1. Integrate Disko declarations without hiding destructive disk operations.
2. Integrate nixos-anywhere for remote installation.
3. Implement `noxctl apply` as evaluate → build → diff → temporary activation →
   health check → confirmation.
4. Add generation inspection and rollback, including connectivity timeout
   handling for remote hosts.

### Phase 3 — runtime and applications

1. Add `noxd` only after the CLI contracts stabilize.
2. Expose HTTP/JSON over a Unix socket; use SQLite for observed state only.
3. Add Podman/Incus adapters and a signed app manifest format.
4. Keep app data, secrets, storage, backups, and network exposure owned by
   Nox rather than hidden inside containers.

### Phase 4 — desktop, workspace, and server depth

Add desktop/gaming, WSL, workspace backends, ZFS/Btrfs presets, SMB/NFS,
backups, and a web UI through the same API. Do not build a custom runtime or
marketplace before the core lifecycle is reliable.

## Explicitly deferred

Custom hypervisor, custom container runtime, custom filesystem, custom
partitioner, custom distributed database, Kubernetes distribution, package
manager, desktop environment, cryptography, backup format, SDN, Ceph
management, HA scheduler, marketplace payments, cloud control plane, and
mobile applications.

## Definition of done for v1

Nox 1.0 should be able to produce, install, safely upgrade, and roll back a
NixOS-based server or desktop, provide a useful recovery image, support WSL
and isolated workspaces, and expose storage/apps/VMs/containers through stable
contracts. Clustering is explicitly beyond the first stable release.
